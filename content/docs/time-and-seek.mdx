To <Term id="seek">seek</Term> is to set the page to a time `t` in seconds and paint the frame for that time. The renderer never plays the page. For each frame it seeks, takes a picture and moves on. Your page code must be a pure function of `t`.

## Why it exists

A film must come out the same on every render, in any order, on any number of workers. A page that plays in real time cannot do this, because the wall clock differs on every run. A seek has no wall clock: frame 400 needs only the number 6.667, not frame 399.

This is also why vawe can render slices of a film in parallel, and render again only the seconds that you changed. See [Determinism](/docs/determinism).

The function `seekTo` in `core/engine/page-seek.js` does one seek, in this order:

1. It waits for the page to start (image decodes, `fetch` and the fonts) and for `document.fonts`.
2. It sets the <Term id="virtual-clock">virtual clock</Term> to `t`.
3. It calls `window.seek(t)` when your page defines it. It waits only for a native `Promise`.
4. It pauses every CSS animation and Web Animation and sets its `currentTime` to `t * 1000` milliseconds.
5. It seeks every SVG animation with `setCurrentTime(t)`.
6. It calls every hook that you registered with `vawe.onFrame`.

After the seek, the renderer waits for fonts, for image decodes and for two real paints. Then it takes the screenshot.

### Two ways to move

You can use either way, or both in one page.

| way | you write | the renderer does |
|---|---|---|
| CSS and Web Animations | `@keyframes` or `element.animate()` | It sets `currentTime` on each animation. |
| `window.seek(t)` | A function that paints the frame for `t` | It calls the function on every seek. |

Use `window.seek(t)` for canvas, three.js and anything else that CSS cannot move. In `window.seek` and in `onFrame` code, use `easeFn(name)` from `core/motion/presets.js` for a named ease, because a CSS `linear()` string cannot run there.

### The virtual clock

Before any page script runs, `core/engine/page-clock.js` replaces these APIs. They follow the seek time.

| API | What the page sees |
|---|---|
| `Date`, `performance.now` | The film time in milliseconds. |
| `requestAnimationFrame` | Callbacks run once for each seek, with the film time. |
| `setTimeout`, `setInterval` | They fire when the seek passes their due time, in due order. |
| `Math.random` | A seeded generator. It starts again from `t` on each seek, so the same `t` gives the same numbers. |

A page that reads the clock still gets the seek time. Do not rely on this. Write each value as a function of `t`, and use `rng(seed)` from `core/motion/springs.js` for a value that must look random but stay the same. See <Term id="seeded-random">seeded random</Term>.

## Frames and rates

The render rate is not part of the page. A draft renders at 30 fps and a final at 60 fps. The script `harness/media/render-page.mjs` takes `--fps N` for another rate. The number of frames is `round(duration x fps)`, and frame `i` shows the time `from + i / fps`, where `from` is the `--from` second of a draft window. At 60 fps, 1.2 s is frame 72.

`<meta name="fps">` is a different thing. It is the rate of your own frame tables, and the page reads it as `window.vawe.fps`. A page can seek at a time that is not a whole frame, for example for motion blur, which blends up to 32 subframes for each frame of a final. For this reason, write a table in seconds or in your own frame rate, and never assume that `t` is a multiple of `1 / 60`.

## An example

This page moves a bar with a Web Animation and a count with `window.seek`. Both use `t` only.

```html
<meta name="duration" content="3">
<div data-world="s1"><div id="bar"></div><p id="n"></p></div>
<script type="module">
  document.getElementById('bar').animate(
    [{ transform: 'scaleX(0)' }, { transform: 'scaleX(1)' }],
    { duration: 2000, fill: 'both' });
  window.seek = (t) => {
    document.getElementById('n').textContent = Math.round(Math.min(1, t / 2) * 100);
  };
</script>
```

The same `t` always gives the same bar and the same number, so you can seek to 1.2 s, then to 3.0 s, then back to 1.2 s, and see the same frame.

## Limits

- State between frames does not work. `x += dx` gives a different value for each order of seeks. Frame 400 must not need frame 399.
- A module-level `await` of something other than an image decode, a `fetch` or `document.fonts.ready` is not waited for. The renderer can paint frame 0 before your `vawe.onFrame` exists. If the renderer waits too long, it stops with the name of what is pending, after 10 s.
- A `window.seek` that never resolves, or a font that never loads, stops the render after several tries of the slice.
- `window.seek` returns a value that the renderer ignores, unless it is a native `Promise`. A GSAP timeline has a `then()` that never settles, so the renderer does not wait for it.
- A `@keyframes` rule with no `100%` stop slides back after it ends. A `fill: both` on an animation with a delay shows the first keyframe from frame 0.

The `anim-traps` gate finds these and more:

```bash
bin/vawe check anim-traps films/<name>/page.html
```
